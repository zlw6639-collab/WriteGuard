# 假绿、元验证与证据四态

> 一个 PowerShell 写护栏项目（WriteGuard）的测试自证笔记。
> 不推销工具，只分享**我们踩过的坑**和**现在怎么判定"证据够不够"**。

---

## 1. 问题：测试全绿，不代表检查有效

先说结论：

> **"检查通过" ≠ "检查有效"。**
> 一个永远全绿的检查器，和没有检查器，在出事那天是一样的。

这个项目里，我们抓到过两类"假绿"。它们长得很不一样，但结局相同：显示 PASS，实际零测试。

### 假绿 I 类：测试没跑

有个候选补丁给 Unix 大小写写了一条用例：

```powershell
if ($IsWindows) { return }
# 之后的断言
$Case = 'pass++'
```

在 Windows 上，`return` 先执行，后面的断言一行都没跑，**但计数器照样加一**。
报告上写 `PASS`，实际执行次数是 0。

我们后来立了一条规矩：**"显示 PASS" 必须等于 "至少执行过一次断言"**。
做不到就别叫测试——叫装饰。

### 假绿 II 类：断言依赖环境

第二份外部审计在 GBK 控制台上跑我们的备份保留测试，结果是 **8/1**；我们本机跑是 9/0。

差异不在代码，在**断言**：测试断言控制台输出里包含 `↳ 保留 N 份`，
而 `↳`（U+21B3）在 GBK 里没有映射，输出时被替换成 `?`。

更糟的还在后面：把代码页换成 cp437（英文 Windows）时，**中文全部变成 `?`**，
CLI 的三条用例一起假红。

这件事之后我们改了测试基础设施：跨进程捕获输出时，**测试自己把输出编码钉死成 UTF-8**，
不再依赖宿主控制台代码页。并且加了一条"敌意控制台"用例——主动把控制台设成 GBK 再断言，
证明"不是恰好我的机器是 UTF-8 才绿"。

教训：**测试断言不能依赖环境默认值**。环境一变就红的测试，和没测一样——只是它红得让人以为是代码有问题。

### 假绿 II 类的同族：父子两端缺一侧

补一个同类的坑，是**审我们的人自己踩的**：他写审计探针时，只在**子进程**钉了 UTF-8，忘了父进程——
宿主 GBK 把子进程的 UTF-8 输出按 GBK 解码，匹配"汇总 / 结果：FAIL"全部落空，
**连对照组都显示"未捕获"**，他第一版差点得出"探针失灵"的错误结论。

修法：父进程也钉。**父子两端缺一侧就是假失败**——和"只钉子进程"是同一个坑的两个方向。

这也是我们后来把测试基础设施改成"函数内 try/finally 钉 + 还原"的原因：
钉一次不够，得钉在**每个会跨进程的调用点上**。

## 2. 元验证：把规矩改坏，看会不会被抓

假绿 I 类最麻烦的地方是：它**看起来**是测试。怎么证明它不是？

我们的办法是**反向验证**（元验证）：把库按某条规矩故意改坏，然后跑测试，看测试**会不会报红**。

```
正常：测试全绿
注入：把"唯一匹配"检查拆掉
期望：测试必须报红，而且必须是"唯一匹配"那条
```

如果注入后测试**照样全绿**，说明那条测试是装饰品。

这套东西跑下来，有两次特别值得说：

**M20 的两次 GREEN。** 我们给"锁的平台断言"设计了一个注入，第一次跑：GREEN（没红）。
第二次换了个注入点：还是 GREEN。最后确认：**这条测试守的是操作系统行为，不是库代码**——
拆库代码根本不影响它。结论是**删掉这条元验证**，并在注释里写明原因，而不是硬造一个假的注入。

**M26 的双层保护。** 编码严格测试有两个保护层：严格解码 + 往返保真。
只拆一层，另一层仍然会抛，所以单点注入永远 GREEN。我们确认这是"测试守整体行为"，
不是"测试弱"——真要让单点注入红，得做组合注入，而我们的框架只做单点。于是也删掉，写明理由。

> **覆盖率不是指标。"每条覆盖都真实依赖被测实现"才是。**

现在我们有 30 个注入场景，并且带一个**噪声场景**：只给代码加一个行尾空格，
测试必须**仍然全绿**（尺子不过敏）。只测"能抓坏"，不测"不误抓"，尺子会过敏。

## 3. 证据四态：别再拿"失败"和"没跑"混着说

做原子写实验时，我们一开始只有两种状态：成功 / 失败。很快就乱了：

- `File.Replace` 被系统拒绝（Access denied）——这是**失败**吗？不，是**实验没跑成**；
- 崩溃注入（断电/被杀）压根**没做**——这是失败吗？不，是**没跑**；
- 但 `File.Move(overwrite)` 跑通了、内容对、时间保留——这才是**通过**。

于是改成四态：

| 状态 | 含义 | 典型场景 |
|---|---|---|
| **PASS** | 跑了，且观察符合预期 | Move 后内容/时间正确 |
| **FAIL** | 跑了，但结果不对 | 并发读者读到半截 |
| **BLOCKED** | 实验**没跑成**（权限/环境阻挡） | File.Replace Access denied |
| **NOT_TESTED** | 实验**没有运行**（缺手段） | 真机断电 |

关键区分：
- **权限拒绝 ≠ 原子写失败**。BLOCKED 不是 FAIL，换一个有权限的环境可以重跑。
- **没跑 ≠ 通过**。NOT_TESTED 不能因为"其他场景都过了"就升级成"安全"。

这个区分后来被用在所有实验资产上：探针输出 JSON，每个场景带 `status` + `observed` + `proves` + `notProven`。

## 4. 证据等级：✅ / 🔍 / ⚪ / ⛔

承诺表上每条对外承诺都标证据等级：

| 等级 | 含义 | 例子 |
|---|---|---|
| ✅ **实际执行** | 在真实环境跑过 | Windows + PowerShell 7 上真跑 |
| 🔍 **策略注入** | 在 Windows 上跑"另一平台语义" | 用 `-CaseInsensitive` 模拟 Unix 大小写 |
| ⚪ **静态检查** | 读过代码，分支没执行 | Unix 专有路径 |
| ⛔ **未验证** | 环境限制或缺探针 | 崩溃注入、原子写断电 |

规则：**没有一条能"因为测试全绿"而升级等级**。
比如"Unix 大小写"这条，跑了注入验证也只能算 🔍，不能算 ✅——因为真实文件系统没跑过。

## 5. 结论：把"敢说什么"写成边界

这个项目最有价值的文档不是 README，是一张**承诺-实现-测试-证据对照表**：

- 40+ 条对外安全承诺，每条都找到实现、失败探针、适用边界；
- 没有证据的承诺（原子替换、崩溃恢复、Unix 锁语义、审计防篡改）单独一节，**明说"不敢保证"**；
- 元验证覆盖的空白单独一节，每条都写"为什么没有"（试过但不红 / 测的是平台 / 本框架不适合）。

一句话：**这张表是"我们敢说什么"的边界，不是"我们做了什么"的清单。**

如果你也在写"自动化改文件"的工具，三条建议：

1. **测试断言别依赖环境默认值**（编码、换行、路径分隔符、console 行为）；
2. **给测试本身做注入**（哪怕只有一个场景），否则你不知道它是检查器还是装饰品；
3. **失败、没跑成、没跑，三件事分开写**——把"没证明"说成"通过"，是项目里最贵的错误。

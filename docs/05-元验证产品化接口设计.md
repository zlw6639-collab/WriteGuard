# 元验证产品化接口设计（0.2.0 唯一候选新功能）

> **状态：设计稿，不写实现。** 审计建议"只做设计，不写实现"——本文就是那个设计。
> 目的：把现在**脚本级**的元验证（`tests/MutationCheck.ps1`，30 个场景硬编码）抽象成**可复用接口**，
> 让别的检查器/项目也能用同一套"注入 → 判定"骨架。
>
> ⚠️ 这不是给 WriteGuard 加功能，是提炼**方法论工具**。判断标准不是"覆盖率涨了多少"，
> 而是"**每条覆盖是否真实依赖被测实现**"。

---

## 0. 现状（为什么要产品化）

`MutationCheck.ps1` 现在的问题：

| 问题 | 现状 | 产品化后 |
|---|---|---|
| 注入点 | 正则写死在场景数组里 | 接口化：`{ 目标文件, 定位方式, 替换, 期望命中数 }` |
| 判定 | 读测试报告的 `FAIL` 行 | 接口化：检查器必须返回**机器可读**的失败项（id + 状态） |
| 证明注入发生 | 命中数 = 1 | 接口化：命中数 + 替换后文件 hash 变化 |
| 框架错误 | `INJECT-MISS` / 跑不起来 | 接口化：错误分类（框架错误 ≠ 检查器拒绝） |
| 输出 | 文本报告 | 接口化：JSON（场景、注入、判定、证据引用） |

## 1. 六要素（审计给的口径，逐条落成接口）

### 1.1 声明检查器（Checker）

```jsonc
{
  "id": "self-test",
  "kind": "checker",
  "entry": "pwsh -NoProfile -File ./tests/SelfTest.ps1",
  "inputs": { "modulePath": "string" },
  "verdict": {
    "pass": "exit 0 且报告含 PASS N / FAIL 0",
    "fail": "exit 1 且报告含 FAIL 行（每行以「FAIL  用例名」开头）",
    "frameworkError": "exit 2 或报告缺失/格式变化"
  }
}
```

**要求**：检查器的失败项必须**可枚举**（不是只给退出码）。没有可枚举失败项的检查器，产品化后只能得到"红了/没红"，无法验证"红的是不是该红的那条"。

### 1.2 定义注入点（InjectionPoint）

```jsonc
{
  "id": "M4",
  "target": "WriteGuard.psm1",
  "locator": { "kind": "regex", "pattern": "…", "expectedHits": 1 },
  "replacement": "…",
  "expectFail": "⑭ 只改唯一匹配"
}
```

- **定位方式**：`regex`（现行）/ `byteRange`（未来，与字节 span 原型对齐）/ `lineRange`（最稳，但脆）。
- **`expectedHits = 1`**：命中 0 次或多于 1 次 ⇒ **框架错误**（`INJECT-MISS`），不是"通过"。
- 注入只改**临时副本**，绝不碰真文件（现有实现已如此，接口化后写进契约）。

### 1.3 证明注入发生（Proof）

三层，缺一不可：

| 层 | 检查 | 失败含义 |
|---|---|---|
| ① 注入点命中 | 命中次数 == `expectedHits` | 库代码变了，定位失效 ⇒ 框架错误 |
| ② 注入内容变化 | 替换后文件 SHA256 ≠ 原文件 SHA256 | 替换没生效（如模式匹配了但替换字符串相同）⇒ 框架错误 |
| ③ 注入确实生效 | 检查器失败项里出现 `expectFail` | 检查器没抓到 ⇒ **GREEN（最坏：检查器撒谎）** |

> ⚠️ ② 是关键补丁：只验证"命中"不验证"内容真的变了"，可能在"替换成同一个字符串"时静默通过。

### 1.4 执行判定（Verdict）

| 检查器结果 | 判定 | 说明 |
|---|---|---|
| 红，且红的是 `expectFail` | **OK** | 注入生效、检查器按预期拒绝 |
| 全绿（exit 0） | **GREEN**（最坏） | 检查器是装饰品 |
| 红了，但不是期望项 | **WRONG-CASE** | 另有覆盖点，需人工看 |
| 检查器没跑成（exit 2 / 报告缺失） | **FRAMEWORK-ERROR** | 不能当"通过"，也不能当"检查器有效" |

### 1.5 区分拒绝与框架错误（Error taxonomy）

```
OK               注入生效，检查器按预期拒绝
GREEN            注入生效，检查器仍全绿（最坏）
WRONG-CASE       注入生效，检查器红了但不是期望项
INJECT-MISS      框架错误：注入点命中数 ≠ expectedHits
FRAMEWORK-ERROR  框架错误：检查器跑不起来 / 报告格式变化 / 超时
NOISE            噪声场景：注入无关改动，检查器必须仍全绿（尺子不过敏）
```

**硬规则**：`INJECT-MISS` / `FRAMEWORK-ERROR` **不能**计入"OK"。它们说明**尺子坏了**，结论不可信。
（现行脚本用退出码 2 区分，产品化后写进 JSON 的 `category`。）

### 1.6 机器可读输出（JSON）

```jsonc
{
  "schema": 1,
  "tool": { "name": "mutation-check", "version": "0.2.0" },
  "generatedAt": "2026-10-18T…",
  "checker": "self-test",
  "summary": { "ok": 29, "green": 0, "wrongCase": 0, "injectMiss": 0, "frameworkError": 0, "noise": 1 },
  "scenarios": [
    {
      "id": "M4",
      "injection": { "target": "…", "hits": 1, "beforeSha": "…", "afterSha": "…" },
      "verdict": "OK",
      "failedItems": ["⑭ 只改唯一匹配"],
      "evidence": { "checkerReport": "…", "log": "…" }
    }
  ]
}
```

- `beforeSha`/`afterSha` 是 1.3 ② 的证据；`failedItems` 是 1.4 的证据。
- 不含绝对路径（脱敏规则见 06 文档）。

## 2. 迁移路径（两阶段，不激进）

**阶段一（包装，不改现有脚本语义）**：
- 新增 `tests/mutation-lib.psm1`（或函数库），导出 `Invoke-MutationScenario`；
- `MutationCheck.ps1` 内部改为调用它，场景数组格式不变；
- 现状 30 场景全部仍走原路径，输出增加 JSON（可选开关 `-ReportJson <path>`）。

**阶段二（接口化）**：
- 场景声明从 PowerShell 数组抽成 JSON（`tests/mutations.json`）；
- 提供 `Invoke-MutationSuite -Checker <path> -Mutations <json> -Out <json>`；
- 别的项目可复用（只要它的检查器能返回可枚举失败项）。

**验收判据（将来实现时）**：
1. 30 场景在阶段一后行为**完全一致**（同 OK 数、同 GREEN 数）；
2. `INJECT-MISS` 时退出码 2、JSON `category=INJECT-MISS`，且**不**计入 OK；
3. 注入到噪声场景（`Set-StrictMode` 加空格）仍全绿；
4. JSON 可被 `ConvertFrom-Json` 解析，字段齐全。

## 3. 不做的（明确边界）

- **不做**"自动修复注入点"——定位失效应报错，让人改代码/改正则；
- **不做**"覆盖率评分"——覆盖率不是指标（M20/M26 的两次 GREEN 就是反例）；
- **不做**"跨语言通用注入器"——先服务 PowerShell 检查器，别的语言留接口不承诺；
- **不写实现**（本文档阶段）。
